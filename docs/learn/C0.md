# C0 in plain words: how one frame gets made

Read this alongside the code. Each section names the file it explains.

## 1. Who does what

Your JavaScript runs on the **CPU**. It doesn't draw anything itself. It *describes* work and hands it to the **GPU**, which runs thousands of copies of a small program (a *shader*) in parallel, one per pixel.

Each frame, `main.ts` does four things:

1. `hud.frame(...)` updates the stats.
2. `pass.encode(...)` writes this frame's camera into a GPU buffer, then records "draw a triangle with this pipeline".
3. `device.queue.submit(...)` sends the recorded commands to the GPU.
4. The browser shows the finished image at the next screen refresh, and `requestAnimationFrame` calls us again.

C++ analogy: building a command list and submitting it to a queue, like in Vulkan or D3D12. WebGPU is designed on the same model.

## 2. Getting a GPU (`platform/detect.ts`, `gpu/device.ts`)

The chain is `navigator.gpu` → **adapter** (a physical GPU the browser offers) → **device** (our private connection to it).

There are three ways it can fail, and we explain each one differently:

- **Not a secure context.** WebGPU only exists on `https://` or `localhost` pages. On other pages `navigator.gpu` is simply missing, which is why that check runs first.
- **No `navigator.gpu`.** The browser or OS doesn't support WebGPU yet.
- **`requestAdapter()` returns `null`.** WebGPU exists but no usable GPU was offered: a blocked driver, hardware acceleration turned off, or a remote desktop session.

The decision logic, `diagnose()`, is a pure function of plain facts, which is why it can be unit-tested in Node without a browser.

## 3. The canvas (`gpu/canvas.ts`, `main.ts`)

- **`context.configure({ device, format })`** connects the canvas to our device.
- **Every frame, `context.getCurrentTexture()`** hands us a fresh texture to draw into.
- **`format`** comes from `getPreferredCanvasFormat()`, the layout the display handles most efficiently.

A canvas has two sizes:

- its size **on the page**, in CSS pixels;
- its **drawing buffer**, `canvas.width`/`canvas.height`, in real pixels.

On a high-DPI screen one CSS pixel can be 1.5 or 2 real pixels. `trackCanvasSize` keeps the drawing buffer equal to the real pixel count, so the image is sharp.

## 4. The full-screen triangle (`render/whitted.wgsl`, `vs`)

We want the fragment shader (the per-pixel program) to run once for every pixel. The GPU only runs it for pixels covered by triangles, so we draw one triangle bigger than the screen:

```
 (-1,3)
   |\
   | \
   |  \          the screen is the square -1..1
   +---\----+
   |    \   |
   |     \  |
   +------\-+
 (-1,-1)   (3,-1)
```

The GPU clips off the parts outside the screen. There's no vertex buffer: the vertex shader computes the three corners from `vertex_index` (0, 1, 2).

## 5. From a pixel to a ray (`fs`)

1. **Find the pixel's position.** `@builtin(position)` gives the pixel center in canvas pixels, with y pointing down. We convert it to −1..1 with y pointing up.
2. **Aim through an imaginary screen.** Imagine a screen one unit in front of the camera. Its half-height is `tan(fov/2)` and its half-width is that × aspect ratio.
3. **Build the direction:** `forward + right·x·halfWidth + up·y·halfHeight`, normalized.

The camera's `forward`, `right` and `up` come from `camera/orbit.ts`, which turns two angles and a distance into a position and three directions.

## 6. Does the ray hit anything? (`intersectSphere`, `intersectGround`)

A ray is `origin + t·dir`, where t is the distance travelled.

- **Sphere:** solve `|origin + t·dir − center|² = r²`. That's a quadratic in t.
  - A negative discriminant means a miss.
  - Otherwise there are two roots, entering and leaving. We take the smallest one that's in front of us.
- **Ground (y = 0):** `t = −origin.y / dir.y`. It only counts if the ray is heading down.

`intersectScene` tests every object and keeps the closest hit. That's fine for 6 objects. A million triangles needs a BVH: a tree of boxes that lets a ray skip most objects. That's Act 2.

## 7. Shadows and reflections (Whitted, 1980)

At a matte surface we start a second ray toward the sun. If it hits anything, the point is in shadow. These shadows are *computed per pixel, per frame*, and that's why they move as the sun circles.

At a mirror we compute the reflected direction and keep tracing, up to 4 bounces. That's why the mirror ball shows the gold ball, which shows the mirror ball.

**Why `EPSILON`:** a new ray starts exactly on the surface it left. Floating-point rounding can put the start slightly *inside* the surface, and the ray immediately "hits" it. That makes speckled false shadows, called "shadow acne". Nudging the start point off the surface fixes it.

**What's fake:** the `ambient` term. Real light also bounces off the ground and the sky onto everything, and Whitted tracing doesn't compute that. C1's path tracer does it properly, by sending random rays and averaging them.

## 8. From light to pixel values (`toneMap`, `encodeSrgb`)

The shader computes *physical* light amounts, which can be far above 1 (the sun disk is about 6). A screen can only show 0..1.

- **Tone mapping** squeezes the full range with a film-like curve, so bright areas roll off smoothly instead of clipping to flat white.
- **sRGB encoding:** screens expect values that are brightness-curved (sRGB). Our canvas format stores numbers as-is, so we apply that curve ourselves. Skip it and everything looks too dark and harsh.

## 9. Passing data to the shader (`render/frame-uniforms.ts`)

The camera changes every frame, so each frame we write it into a **uniform buffer**, a small block of GPU memory the shader reads as `var<uniform> frame`.

The bytes must line up exactly with WGSL's `struct Frame`. The catch is that **WGSL aligns a `vec3f` to 16 bytes**, not 12. So after every 3-float vector there's a 4-byte gap, and we put a useful single float there instead of wasting it:

```
offset (floats):  0  1  2 | 3            4  5  6 | 7       ...
                  cameraPos | tanHalfFovY  cameraRight | aspect ...
```

The unit test in `frame-uniforms.test.ts` locks this layout down. If someone reorders the struct and not the packer, the test fails instead of the picture silently breaking.

Spec: https://www.w3.org/TR/WGSL/#alignment-and-size

## 10. When things go wrong

- **WebGPU calls don't throw.** Mistakes are reported asynchronously. We log any that nobody else caught (`uncapturederror`, in `gpu/device.ts`).
- **Shader compile errors** are printed with file, line and column (`logCompilationMessages`, in `whitted-pass.ts`).
- **Device loss:** the GPU can be reset under us, for example by a driver crash or update. Every GPU object then becomes useless, so we start over from a new adapter. If that happens more than 3 times a minute, we stop retrying and explain why, rather than flickering forever.
