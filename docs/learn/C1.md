# C1 in plain words: from one ray per pixel to a path tracer

Read this alongside the code. Each section names the file it explains. C1 is being built in chunks (see `docs/PLAN.md`); this note grows with each one.

## Chunk 1: an image that refines itself

### 1. A pixel is a square, not a point (`render/tracer.wgsl`, `fs`)

In C0 each pixel sends one ray through its center and takes the color of whatever is exactly there. But a pixel covers a small square of the scene, and the center is only one point in it. That causes two kinds of trouble, both called **aliasing**:

- **Jagged edges.** A pixel half covered by a ball becomes all ball or all background, depending on which side its center lands. Along an edge that makes a staircase.
- **Flicker in the distance.** Far away, one pixel covers several checker squares, and its center lands on a black or white one more or less by chance. Move the camera and that chance changes every frame.

The fix is **anti-aliasing**: send rays through several points inside the pixel and average them. A pixel can still only show one color, but it becomes the *average* color of its square. An edge pixel gets an in-between shade, and your eye reads a row of those as a smooth edge. Text on screen is smoothed the same way.

The first sample still goes through the pixel center, so while the camera moves the image looks exactly like C0. Later samples go through random points in the square; moving a sample point like this is called **jitter**.

### 2. Random numbers on a GPU (`pcgHash`, `random`)

Shaders have no `Math.random()`, and thousands of pixels run at once, each needing its own unrelated numbers. The standard answer is a **hash function**: a few multiplications, shifts and XORs that scramble a number, so that 1 and 2 come out completely unrelated.

- **Seeding.** Each pixel hashes its x, its y and the sample number together to get a starting state (`seedRandom`). Every pixel gets a different sequence, and so does every sample.
- **Drawing numbers.** Each call to `random()` hashes the state again and turns 24 of its bits into a float in [0, 1). Only 24, because an f32 holds exactly 24 bits of precision; using all 32 could round up to exactly 1.0.
- **`var<private>`.** The state lives in a `private` variable: each pixel's run of the shader has its own copy, like a thread-local variable in C++.
- **It's repeatable.** The same seed always gives the same numbers, which makes bugs reproducible.

The hash is PCG, from Jarzynski & Olano's 2020 survey of GPU hash functions. Anti-aliasing is its first, easy use; in chunk 2 the same numbers choose which way light bounces.

### 3. Progressive accumulation (`render/accumulation.ts`, `render/tracer-pass.ts`)

Sending 64 rays per pixel every frame would make every frame 64 times slower. Instead we send one per frame and **remember the running total**:

- **Frame 1** stores its sample. **Frame n** adds its sample to the total and shows `total ÷ n`. The image gets smoother every frame the camera stays still; the HUD's "Samples" line counts them.
- **The total lives on the GPU** in a storage buffer with one `vec4f` per pixel, about 33 MB at 1920×1080. The fragment shader reads its pixel's slot, adds to it and writes it back (`var<storage, read_write>`). That's safe because each pixel only ever touches its own slot.
- **Starting over.** If anything that changes the picture changes (camera, canvas size, sun, renderer, view, scene), the old total belongs to a different image. `createSampleCounter` compares this frame's inputs with last frame's and returns 0 when they differ, which tells the shader to overwrite instead of add. That's why "Sun moves" now starts off: a moving sun would restart the total every frame.
- **Stopping.** After 1,024 samples more make no visible difference, so `main.ts` stops drawing. The canvas keeps showing its last image until something changes, and the GPU rests.
- **Choosing how many.** The panel's "Samples" menu (1, 4, 16 … 1024) sets where it stops, like a game's "4x" or "16x" supersampling. A game takes all of its samples inside every frame; we take one per frame and add them up over time, which is far cheaper but only works while the image holds still.
- **Big screens.** By default WebGPU lets a shader use at most 128 MB of one storage buffer, enough for about a 4K canvas. `createDevice` asks for whatever larger limit the GPU offers. If the canvas still doesn't fit, the image just doesn't refine, and the console says why.

This repeated averaging is what C1 is really for. A path tracer's single frame is very noisy, because each pixel follows only one random light path; averaging hundreds of them gives a clean image. Anti-aliasing is the test case, because you can see at a glance whether it works.

### 4. Average light, then tone map (`fs`)

The order matters. Take an edge pixel that's half sun disk (light value 6) and half dark ground (0.05):

- **Average the light, then tone map:** (6 + 0.05) ÷ 2 ≈ 3.0, which tone maps to 0.95. The pixel is bright.
- **Tone map each sample, then average:** 0.99 and 0.04 average to 0.52. The pixel is mid-grey.

A camera sensor collects light first and the film or software responds to the total, so the first is right. It's part of why small, very bright lights look bigger than they are in photos. So `fs` keeps the running total in linear light and only tone maps the average.

### 5. Seeing it for yourself (`scene/layouts/aliasing-test.ts`)

The `aliasing-test` scene is built from things that alias badly:

- **A fine black-and-white checkerboard** stretching to the horizon. Far away, many squares fit in one pixel, and one sample per pixel picks among them in a pattern that drifts into false wavy bands called **moiré**.
- **A mirror ball**, whose curve squeezes that checkerboard into even finer stripes.
- **A dark ball against the bright sky**: the clearest stair-stepped edge.
- **A row of beads** marching away, until they're smaller than a pixel. With one sample they blink in and out as you orbit, because a sample either hits a bead or misses it.

Things to try in the panel's Anti-aliasing section:

- Flip "Samples" between 1 and 16, and between 16 and 1024. Most of the improvement comes early: the error shrinks with the square root of the sample count, so 4 samples halve it, but halving it again takes 16.
- Set "Pace" to "One at a time" and press "Next sample" to watch each jittered sample land. Or pick "4 per second" to watch the image build up.

## Chunk 2: real light

The Renderer menu switches between C0's Whitted tracer (`traceWhitted`) and the path tracer (`tracePath`), both in `render/tracer.wgsl`. Flip between them on `ball-test-1` to see what real light adds.

### 6. Following light backwards (`tracePath`)

Light leaves the sun, bounces around the scene, and a tiny fraction of it ends up in the camera. Simulating that forwards would waste almost every ray, so a path tracer works **backwards**: from the camera, through a pixel, into the scene, bouncing from surface to surface until it reaches a light. Light paths work the same in both directions, so the answer is the same.

At each matte surface, the path:

1. **asks the sun directly:** one shadow ray toward the sun. If nothing blocks it, the sunlight arriving there is added, dimmed by the surface's color and by everything earlier on the path. This is called **next-event estimation**. A bounce ray would almost never find the sun by chance, since it's tiny in the sky, so it's asked directly every time.
2. **bounces on** in a random direction, and keeps going.

When the path escapes to the sky, the sky's color *is* the light arriving from that direction, so it's added too. That's what replaced C0's fake `ambient`: shadows are now lit by the sky (which is why they're bluish), and corners and contact points get less of it, because the objects around them block part of the sky. Light that bounces off the red ball and lands on the floor tints it red: **color bleeding**.

`throughput` is how much of the light found further along still reaches the camera. Each matte bounce multiplies it by the surface's albedo, each mirror by its tint.

### 7. Which way to bounce (`randomUnitVector`)

A matte surface scatters light more toward its normal than sideways: Lambert's cosine law again. So bounce directions near the normal are chosen more often, in proportion to the cosine (**cosine-weighted sampling**). There's a neat trick for it: picture a ball of radius 1 resting on the surface, pick a random point on that ball, and aim at it. That spreads directions exactly by the cosine.

Choosing directions in proportion to how much they matter is **importance sampling**, and it's why each bounce simply multiplies by the albedo, with no extra weighting. The general rule behind it: a random estimate stays correct on average as long as each sample is divided by how likely it was to be picked. Here that division and the cosine cancel out.

### 8. Soft shadows from a sun with a size (`sampleSunDirection`)

The real sun isn't a point: it's a disk about 0.53° across. C0 aimed every shadow ray at its center, so a point was either fully lit or fully shadowed, giving razor-sharp edges. Now each shadow ray aims at a random point on the disk. Near a shadow's edge some of those rays are blocked and some aren't, and the average is a soft transition, the **penumbra**. It widens with distance from the object: about 1 cm for every meter between the object and the ground, so with these small scenes it's subtle up close and clearer under the floating ball in `aliasing-test`.

The disk drawn in the sky now uses the same real size, so what you see matches what casts the shadows.

**Not counting the sun twice.** The shadow rays already add the sun's light, so when a *bounce* ray happens to hit the sun disk, the disk is left out (`sky(..., withSunDisk)`). Otherwise that light would be counted twice. Camera rays, and mirror reflections of them, still see the disk.

### 9. Russian roulette

After a few bounces, a path carries little light, but following it costs as much as ever. So paths are ended at random, more often the less light they carry, and the survivors are brightened by exactly the chance they had of surviving. On average the image is unchanged; the GPU just stops spending time on paths that hardly matter.

### 10. What's still missing

- **Caustics.** Sunlight focused by the mirror balls onto the floor (the bright patches a glass of water throws) needs a path that bounces off a matte surface, hits a mirror and then the tiny sun disk, and random bounces almost never find that. Dedicated techniques exist; they're out of scope for now.
- **The sky's brightness is a guess.** Next to the sun, our painted sky is too bright: it lights a surface with roughly a third to a half as much light as the sun does, where a real clear sky gives a tenth to a fifth. So shadows come out a little washed out. Per-scene sun and sky settings, or a photographed sky (HDRI), would fix it.

### 11. GPU timing (`gpu/timer.ts`, HUD)

The HUD's "Frame" line is the time *between* frames, which your display's refresh rate caps (6 ms at 165 Hz) no matter how little work there is. The new "GPU time" line is the time the GPU actually spends drawing a frame, measured with **timestamp queries**: the GPU writes its own clock at the start and end of the render pass, and the two values are copied back to the CPU.

It shows **percentiles** of the last 120 measured frames: p50 is a typical frame, p95 and p99 are the slow ones. Averages hide stutter; a p99 of 30 ms means one frame in a hundred takes 30 ms, which you feel as a hitch even if the average is fine.

The values arrive a frame or two late, because the GPU works behind the CPU and the result has to be copied back first. Browsers that don't offer the `timestamp-query` feature show "not measurable" instead of a guess.

### 12. Shadows and height (`scene/layouts/shadow-heights.ts`)

How soft a shadow's edge is depends on how far the shadow falls from the object casting it. Seen from a point near the edge, the object hides part of the sun's disk, and that partial cover is the penumbra. Its width is the distance from the object to the shadow (measured along the sun's direction) times the sun's angular size, 0.0093 radians: about 1 cm per meter.

The `shadow-heights` scene puts this side by side: a row of balls from touching the ground to 3.2 m up, and an orange ball you lift with the slider under the Scene menu. Touching the ground, a shadow is sharp at the contact point; lifted, its edge blurs and the soft sky shadow beneath it fades. The slider works by handing the renderer a changed copy of the scene (`withSphereHeight`), which it uploads like any new scene, restarting accumulation.

### 13. Moving around (`camera/orbit.ts`, `camera/fly.ts`)

Two cameras, chosen in the Camera menu (or by the keys: W, A, S or D switches to Fly, an arrow key back to Orbit). Switching keeps the view: the new camera starts exactly where the old one was.

- **Orbit** circles a target point: two angles and a distance.
- **Fly** floats freely: a position and two angles, moved by WASD each frame by speed × the frame's duration, so the speed is the same at 60 or 165 fps.

**Turning all the way around.** A camera needs a right and an up direction as well as forward. The usual shortcut builds them from "world up" (0, 1, 0), but looking straight up or down, forward lines up with world up, and the cross product that gives "right" collapses to zero. That's why many cameras stop just short of vertical. Ours instead takes "up" to be the direction the view turns as the pitch angle grows, which is always at right angles to forward. Past the top, it simply points downward: the camera is upside down, like one on a ball joint, and left and right drags are swapped to keep feeling natural.

## Chunk 3: boxes and glowing objects

Look at the `neon-night` scene, and flip the Renderer menu between the two renderers.

### 14. Boxes in their own coordinates (`intersectBox`, `math/mat3.ts`)

Testing a ray against a box that's turned at some angle is awkward. Testing it against a box lined up with the axes and centered at the origin is easy. So instead of turning the box, we turn the *ray*: subtract the box's center from the ray's start, and rotate both start and direction backwards by the box's rotation. Whatever the ray hits in those coordinates, it hits in the world. This trick (move the ray into the object's own **local space**) is how renderers handle every kind of moved, turned or scaled object.

The rotation is a 3×3 matrix built on the CPU from the angles in the scene file (`rotationFromDegrees`). Its columns are where the box's own x, y and z axes point. Undoing a rotation is cheap: a rotation matrix's inverse is just its transpose (rows and columns swapped).

In local space the **slab test** finds the hit. A box is where three slabs overlap, each the space between two parallel planes (x between −w and +w, and so on). Along the ray, each slab is entered at one distance and left at another. The ray is inside the box from the *last* entry to the *first* exit; if the last entry comes after the first exit, the slabs never overlap along the ray and it misses. The face hit is the one whose plane gave that last entry, and its direction, turned back into world coordinates, is the normal.

### 15. Glowing objects as lights (`sampleLight`, `lightFromObjects`)

Any material can glow (`emission`). A glowing surface is seen directly as its own color, and it lights everything around it.

Lighting by a glowing object uses the same idea as the sun: at each matte bounce, one shadow ray toward a random point on a randomly picked light. The amount of light it brings depends on:

- the light's brightness at that point;
- **distance squared:** the same light spread over a sphere 2× as far away covers 4× the area, so it's 4× dimmer;
- **the angle at the surface** (Lambert's cosine law, as for the sun);
- **the angle at the light:** a patch of glowing surface seen edge-on shows less of itself.

Each estimate is divided by the chance of having picked that light and that point, which keeps the average right however the picks are made. That freedom is used to pick brighter, bigger lights more often (`findLights` in `scene.ts`), so rays go where most of the light comes from.

As with the sun disk, a bounce ray that happens to hit a light adds nothing (`countLights`), because its shadow ray already counted that light; camera rays and mirror reflections do see lights directly.

The Whitted renderer can't sample random points, so it treats each glowing object as one point of light at its center. That gives hard shadows and no bounce light: compare the shadows behind the mirror balls in the two renderers.

### 16. Night, sheen and puddles (`scene/layouts/neon-night.ts`)

- **Per-scene sun and sky.** A scene can set the sun's color and brightness and dim the sky (`environment`). At night the "sun" becomes a bluish moon, a fifth as bright as daylight, and the neon sign adds the color.
- **A mirror coat.** `reflectivity` makes a matte material reflect part of the light like a mirror: with `reflectivity: 0.05`, each bounce has a 5% chance of reflecting instead of scattering. Choosing at random with exactly those odds is right on average, the same idea as Russian roulette. `neon-night`'s asphalt tried it and dropped it: the sign is so bright that even 2% stood out as a sharp mirror image, while real wet asphalt blurs reflections and fades them when seen from above. That needs roughness and the Fresnel effect, in chunk 4. (`reflectivity` is gone now; see section 22.)
- **Puddles** are very thin mirror boxes lying on the ground. A mirror shows whatever is in the reflected direction, which at night is mostly black sky, so puddles look dark except where they reflect a light.
- **Why the sign looks almost white at its core.** Tone mapping squeezes each color channel separately, so very bright light runs toward white. Cameras do the same with real neon. Keeping the green very low keeps it pink. The colored glow you see around real neon in photos is bloom, a camera effect on the candidates list.

### 17. What it costs

The night scene takes about 16.5 ms of GPU time per sample at 1280×800 on an Intel laptop GPU, three times `ball-test-1`. Every ray is tested against all 40 objects, and the mirror balls send rays on bounce after bounce. Cost grows in proportion to the number of objects; a BVH (Act 2) makes it grow roughly with the logarithm instead.

## Optimization

### 18. Measuring before changing (`scripts/benchmark.ts`)

Guessing what's slow doesn't work well; of three changes below, two predictions were wrong. So every change gets a measurement first.

The surprise was how noisy measurements are. The same code, measured in two runs, differed by up to 13%: a laptop GPU jumps between clock speeds, especially on battery. Removing the frame cap to keep it busy made things worse. What works is measuring **head to head**: alternate the old and new builds in one session and compare each pair, so a clock change affects both about equally. A change counts only if every round agrees on the direction and it's bigger than about 5%.

The check that makes this trustworthy is an **A/A test**: compare a build against itself. A sound method reports about 0%. It's the same idea as a placebo in a medical trial.

### 19. Do expensive work last (`intersectScene`)

A ray used to work out the surface normal each time it found a closer object, even if something closer replaced that object a moment later. Now the loop only remembers which object is closest, and the normal is worked out once at the end. This cut GPU time by 14–23% on every scene, and the images stayed byte-identical. The general rule: keep a search loop as small as you can, since it runs far more often than anything after it.

### 20. Two ideas that didn't help

- **"Any hit" shadow rays** stop at the first blocker instead of finding the closest one. It sounds like an obvious win, but it only saves work on rays that *are* blocked. In open scenes most shadow rays reach the sky, so they test every object anyway. GPUs also run pixels in groups, so one pixel finishing early doesn't free the others.
- **Separate shaders** for each renderer and view. Even a shader with only the path tracer in it showed no clear gain, so the extra complexity wasn't worth building. Testing the best possible case first saved writing it.

## Chunk 4: real materials

Look at the `material-test` scene with the path tracer, and let it refine. From the back: gold, red plastic and glass, each getting rougher from left to right, then a front row of special cases.

### 21. One material, set by numbers (`Material` in `scene.ts`)

A material used to be one of three kinds: matte, mirror or checker. Nothing could sit between matte and mirror, and each new look would have needed another kind and another branch in the shader. Now every surface is described by the same few numbers, following the model used by glTF, the file format imported models will arrive in:

- **`baseColor`:** the surface's color, or a checker pattern. "Checker" used to be a kind of material, but it's really just a way of coloring one.
- **`metallic`:** 0 for a non-metal, 1 for a metal. The difference is physical. Light that enters a metal is absorbed, so all you ever see is its reflection, tinted by the metal. Light that enters a non-metal scatters around under the surface and comes back out in all directions, which is what makes it look matte and colored. Its reflection sits on top and stays the color of the light.
- **`roughness`:** 0 is polished, 1 blurs reflections completely.
- **`transmission`:** the share of a non-metal's light that passes through it instead of scattering. 1 is glass.
- **`ior`:** the index of refraction, which says how much the material slows light down. Higher means more reflection, and glass bends light more.
- **`emission`:** the light it gives off, as before.

Every number has a default, so a matte surface is just `{ baseColor: [0.8, 0.8, 0.8] }`. glTF's default for `metallic` is 1, which suits a file exported from a modeling program. Ours is 0, because most surfaces in a hand-written scene aren't metal.

A material can be part one thing and part another, such as `metallic: 0.5`. At each hit the shader picks one at random with those odds and treats the surface as all that for the rest of the hit, which is right on average.

The Whitted renderer is only kept for comparison, so it stays simple: metals are perfect mirrors and everything else is matte, glass included.

### 22. The Fresnel effect (`fresnel`)

Look straight down into a lake and you see the bottom. Look across it and you see the sky. Every surface does this: it reflects more at a grazing angle, and at the very edge it's a perfect mirror. In `material-test`, the dark floor shows it clearly: nearly black at your feet, a mirror toward the horizon.

glTF uses a short approximation of the real equations, by Christophe Schlick:

```
F = F0 + (1 − F0) · (1 − cosine)^5
```

`cosine` is 1 looking straight at the surface and 0 at the edge. **F0** is how much it reflects head-on:

- **Non-metals:** `F0 = ((1 − ior) / (1 + ior))²`. At ior 1.5, which suits most plastic and glass, that's 4%. At 80° from head-on, F is already about 41%. Water's 1.33 gives 2%, and diamond's 2.4 gives 17%.
- **Metals:** F0 is `baseColor`, a different value for red, green and blue, which is why gold reflections look gold. At the edge F reaches 1 for every color, so a gold ball's rim turns white.

A non-metal is a matte surface under a clear layer that reflects a share F of the light. The fixed `reflectivity` number is gone, because it was a stand-in for this: real reflections fade when seen from above, and a fixed number can't.

A bounce picks either the reflection or the matte layer at random. It doesn't use F as the odds, because a black floor at 4% would rarely see its own reflection, which is nearly all there is to see. It favors whichever looks brighter from here (`specularChance`) and corrects for that in the weight: dividing by the chance of what happened keeps the average right, however the choice is made.

### 23. Roughness: millions of tiny mirrors (`scatterToward`, GGX)

Treat a surface as millions of tiny mirrors. On a polished surface they all point the same way, so the reflection is sharp. On a rough one they scatter, so it blurs. Roughness doesn't change how much light comes back, only how far it spreads, which is why a rough highlight is wider and dimmer.

For light to travel from a direction `dir` to the viewer, a tiny mirror must face exactly halfway between them. glTF's formula has three parts:

- **D, the GGX distribution:** how many mirrors face that way. Its long tails give highlights the soft glow around their core.
- **V, visibility:** how many of those aren't hidden by neighboring bumps.
- **F, Fresnel:** how strongly each one reflects.

glTF squares `roughness` to get GGX's width, `alpha`, so the slider feels even.

A bounce shouldn't pick just any tiny mirror, because many face away from the viewer. `sampleVisibleNormal` picks only ones the viewer can see, using a neat trick: stretch space so the mirrors' shape becomes a plain half sphere, pick a point there, and stretch back. Fewer bounces are wasted, so there's less noise.

### 24. Finding light two ways (`misWeight`)

There are two ways to find a light, and each is good where the other is bad:

- A **shadow ray** aims at a random point on the light. On a nearly polished surface most of those points reflect nothing, and now and then one lines up and gives a huge value.
- A **bounce ray** goes the way the surface likes to reflect. On a rough surface it rarely hits a small light, and the rare hit gives a huge value.

The two can't simply be added, or each light would be counted twice. **Multiple importance sampling (MIS)** counts both, and gives each a share of the credit based on how likely each method was to find that light. The shares add up to 1. A lucky hit from a method that was unlikely to find that light gets almost no credit, so the huge values shrink. That's what removes the bright specks. MIS needs no extra rays, because every hit already sends both.

For this to work, both methods must see the same light. Shadow rays deliver the sun's real energy, but the sun disk painted in the sky was over 10,000 times too dim, because it only had to look right. So the path tracer now uses the sun's real brightness (`sunDisk`). You can see it in a chrome ball: the sun's reflection is a tiny, blinding point.

To test MIS, render the same scene with shadow rays only, with bounce rays only, and with both. All three must average to the same brightness, and they did, to within 1%.

### 25. Glass (`sampleGlass`)

Glass reflects a share F of the light and lets the rest through. A ray does one or the other at random with exactly those odds.

Going through, the ray bends by **Snell's law**, which WGSL's `refract()` works out. A glass ball acts as a lens, so what you see through it is upside down. Rays start on the far side of the surface, and the shader must tell whether a ray is going in or coming out, because the bend reverses.

Leaving glass at a shallow angle, a ray can't get out at all, and reflects back inside instead: **total internal reflection**. It's what makes the bright rim inside a glass ball, and how optical fibers work.

Rough glass is the same with tiny mirrors: each one bends the ray its own way, and the view through it blurs. That's frosted glass.

Light through glass is the path tracer's weak spot. A shadow ray travels in a straight line, and glass bends light, so a shadow ray stops at the glass as if it were solid. The floor under a glass ball gets only the light a random bounce finds through it. That's enough for the sky, but the tiny sun is found almost never. So glass casts a shadow that's too dark, with none of the bright patches of focused light (**caustics**) that a real one throws.

### 26. Taming fireflies (`limitScattered`)

Sometimes a path bounces off a matte floor, passes through glass, and by pure luck hits the sun, which is thousands of times brighter than anything else. The right average is small, but that one sample is a bright dot on screen, a **firefly**, and it fades only slowly as samples pile up.

So once a path has scattered off something rough, each step can add only a limited amount of light. This is a deliberate trade: it removes a little real light in exchange for a clean image. Across three test scenes, it removed 64–100% of the stray bright pixels and dimmed the image by at most 0.2%. Film renderers do the same thing.

### 27. Checking the physics

Looking right isn't the same as being right, so two tests go beyond looking:

- **The white furnace.** Put an object in a sky of exactly 1 in every direction. If a surface keeps all its energy, it vanishes: you can't see a mirror's shape if everything it reflects is the same color. Polished glass and mirrors vanished exactly.
- **Knowing the answer.** Very rough surfaces don't vanish, because a model of tiny mirrors loses the light that bounces between them. For a white metal at roughness 1, the sum works out to 1 − ln 2 = 0.307 of the light. The render gave 0.305. That's the cost of a known simplification, and why very rough metal and glass look a little too dark.

The older check still helps: the random numbers come from the pixel and the sample number, so the same code gives the same image, byte for byte. The Whitted renderer and the debug views stayed byte-identical through all of this.

## The dreamspace room

The hall in `src/scene/layouts/dreamspace.ts` is the first scene meant to look like a photo instead of a test. Open it with `?scene=dreamspace`.

### 28. Patterns that follow the wall (`flatten`)

The checkerboard used to read only a point's x and z. That's right for a floor, but going up a wall, x and z stay the same and only y changes, so the squares stretch into stripes.

`flatten` looks at which way the surface faces and throws away that axis: a floor keeps x and z, and a wall keeps the two directions that run across it. The ground still gets x and z, so every older scene came out byte-identical.

There are only three choices, so this suits flat, square-on surfaces. On a sphere, the pattern would jump where the facing axis changes.

### 29. Tiles (`tileAt`)

A **procedural** pattern is worked out by a formula, with no image file. `tileAt` divides the flattened position by the tile size. The whole part says which tile a point is on, and the fraction says where on that tile. Near the edge of the fraction, it's grout.

Real tiles differ, and that's a big part of why they look real. Each one needs its own slight shade and angle, and that needs a number that's fixed for that tile but unrelated to its neighbors'. That's a job for a hash, the same `pcgHash` that makes the random numbers. Here it's fed the tile's coordinates, so it gives the same answer in every sample. If it used `random()`, a tile's shade would change from sample to sample and average out to nothing.

The angle matters more than the shade. The lean is at most ±0.3°, too small to see directly, but a reflection is a long lever. Over 10 meters, that's enough to shift a reflection by up to 20 cm between two tiles, so a reflection in the wall breaks up at each tile, as in a real tiled room.

Grout changes the surface as well as the color. `surfaceAt` makes it rough, so it doesn't shine like the glaze beside it.

### 30. Building the room

Four things in the layout aren't obvious:

- **Light adds up in a white room.** A surface that reflects a share ρ of its light sends ρ on to the next wall, then ρ² after that, and so on. The total is 1 / (1 − ρ) times the direct light. At ρ = 0.8, that's 5 times, and the first render came out flat and washed out, with the sun hardly visible. At ρ = 0.6, it's 2.5 times, and with dimmer panels too, the sun stands out. A camera would also lower its exposure, but this renderer has no exposure setting yet, so the tile is darker than real white tile.
- **No haze indoors.** `haze` fades far surfaces toward the sky color, which is fine outdoors. In a room it would tint the walls blue, so it only runs in scenes with a ground plane.
- **Water runs into the walls.** The water box overlaps the pool's sides by 5 cm. If they only touched, a ray arriving there could hit either surface, decided by rounding error. Overlapping means the tile always comes first.
- **The sun lands on the deck, by design.** Water blocks shadow rays, so sun falling on the pool would be lost. The sun comes in at about 42°, so a window top 3.6 m up throws light 4 m into the room, and the deck is 4.5 m wide.

The room is also the slowest scene so far. Every ray is tested against all 34 objects, as in any scene without a BVH, and in a closed room a path can't end by flying off into the sky until it finds a window. The first effect shows in the Whitted renderer, which takes 5 times as long here as on `neon-night`. The second shows in how much slower the path tracer is than Whitted: 3 times here, against 1.7 times there.

### 31. When the picture looks wrong, measure it

The panels' reflections in the pool looked far too bright for water, which reflects only about 2% of the light from above. That could have been a bug in `fresnel`.

The check was to undo the display steps (sRGB, then the tone curve) on the saved pixels, which gives back the scene's brightness, and to compare that with the formula:

| Viewing angle | Formula: F × 3.5 | Measured |
|---|---|---|
| 45° | 0.08 | 0.08 |
| 60° | 0.18 | 0.18 |
| 66° | 0.34 | 0.35 |

The code was right, and the eye was wrong. Display curves lift dim values a lot, so 0.08 of light against a dark teal floor looks much brighter than "8%" sounds. This is also the Fresnel effect at work: the same water reflects four times as much at 66° as at 45°.

## The Cornell box

### 32. A test with an answer (`layouts/cornell-box.ts`)

The [Cornell box](https://en.wikipedia.org/wiki/Cornell_box) comes from a 1984 paper by researchers at Cornell. It's a real box with a red wall and a green wall, lit from the ceiling. They measured everything (the walls, the blocks, the colors, the light) and photographed it with a calibrated camera, so a render can be compared with a photograph. That's the point of it: a picture that looks right might still be wrong.

Open `?scene=cornell-box` and switch the Renderer between Path tracer and Whitted:

- **Whitted** does one line to the camera, one line to the light, and some math. The ceiling is black, because it can't see the light. The shadows are black, and the white surfaces stay white.
- **The path tracer** adds bounces. The ceiling lights up, the shadows fill in, and the side of the tall block facing the red wall turns red, though nothing red shines on it directly.

The layout keeps Cornell's numbers exactly as published, in millimeters, and turns them into a scene with code. That way a test can compare the result with the measurements. The first things that test guards against are a block turned the wrong way, or a room mirrored so the red wall ends up on the right.

### 33. The bug it found

The real value of a test scene is what it catches. Benedikt Bitterli publishes this same scene with the raw image from another renderer, Tungsten, so a scratch copy rebuilt his scene exactly and compared the light, patch by patch. Ours came out 7% dark on average, and 25% dark on the ceiling.

The search is worth reading as a method. Each step removed one explanation:

| Tried | Result | So |
|---|---|---|
| Lift the 8-bounce limit and the firefly cap | No change | Not those |
| Remove the shiny coat | Colors fixed, still dark | Two separate problems |
| Write a tiny CPU path tracer, sharing no code | It agrees with Tungsten | The shader is wrong, not the comparison |
| Direct light only | Matches the CPU tracer | Wrong only in bounced light, on the patches tested |
| Bounce rays only | Matches Tungsten | Geometry and materials are fine; shadow rays lose light |
| Russian roulette off | No change | A good guess, and wrong |
| A better random number generator | No change | Another good guess, and wrong |
| Measure only the second hit | Surfaces that see the block tops lose half | Look at the block tops |
| Look at them | The tall block's top is dark | Found it |

Two of those guesses were reasonable and wrong. Testing them took minutes. Believing them without testing would have left the bug in.

The cause was one line in `lightFromObjects`. A shadow ray can't start exactly on a surface, so it starts 1 mm off it (the fix for shadow acne, in `docs/learn/C0.md`). It also has to stop just short of the light, or the light would count as blocking itself. The code measured the distance from the surface, then stopped 0.1% short.

Facing a light head-on, starting 1 mm closer means reaching the light 1 mm sooner. And 0.1% of the distance is less than 1 mm when the light is less than 1 meter away. So the ray reached the light before it stopped, the light counted as a blocker, and the surface got no light from shadow rays. The top of the tall block is 0.78 m from the lamp, so it failed. The top of the short block is 1.38 m from it, so it worked.

The other scenes hid this because their lights are far from whatever faces them. It only showed here because Bitterli's room is 2 m tall. In our own scaled-up Cornell box, the same block is over 2 m from the light, so that scene would have looked right either way. The bug had been there since glowing objects were added.

The fix measures from where the ray really starts. Scenes with no glowing objects stayed byte-identical. With the fix, and the shiny coat removed to match the reference's purely matte surfaces, every patch is within 1.6% of Tungsten.

The lesson is about numbers that mix scales. A fixed 1 mm and a percentage of a distance only line up at one particular distance, here 1 meter, so anything that depends on comparing them works at some sizes and silently fails at others.

## Less noise for the same work

### 34. Measuring noise (`scripts/noise.ts`, `scripts/image.ts`)

The benchmark measures time, but some changes aim at noise instead: a cleaner picture from the same number of samples. To measure that, render each scene twice: once with few samples (16 and 64), once with many (1,024) as a clean **reference**. The typical difference per pixel between them is the noise. In statistics that's the **root-mean-square (RMS) error**: square each pixel's difference, average them, take the square root.

Two properties make this trustworthy:

- **It's exactly repeatable.** Random numbers come from the pixel and the sample number, so a build draws the same picture every time. Comparing a build against itself gives exactly 0, not "about 0" as timing does.
- **Error falls with the square root of the sample count.** Four times the samples should halve the error, and the measurements do. It also turns an error change into something easier to picture: 30% less error is as good as about 2× the samples, because (1 ÷ 0.7)² ≈ 2.

It also checks that a change doesn't alter the picture. A new build's 1,024-sample picture should differ from the old one's only by their leftover noise. Much more than that would mean it draws something different, a **bias**, which no amount of samples fixes.

The screenshots come back as PNG files, and Node has no PNG reader, so `image.ts` reads them: unzip the data, then undo PNG's row "filters", which store each byte as a difference from its neighbors because differences compress better.

### 35. Aim shadow rays only where light can come from (`sampleLight`, `visibleFaceAreas`)

A glowing box gives off light from each face, but a face only lights what's in front of it. Shadow rays used to aim at a random point anywhere on the box, so a ceiling panel's top face got about half of them, and those could never bring light down to the room. Now each shadow ray aims only at faces the lit point can see.

Which faces can a point see? Move the point into the box's own coordinates, where the box is lined up with the axes. Across each axis there's a pair of faces, and the point can see the one on its side only if it's beyond that face's plane: below the panel, it sees the bottom face but not the top. That's at most three faces, found with one comparison per axis.

The chance of aiming at any one point grows to match, since the same shadow rays now cover less area. MIS (section 24) uses that same chance when a *bounce* ray happens to hit a glowing box, so `intersectScene` works it out the same way, from where the bounce ray started. If the two disagreed, light would be counted wrongly.

Results at 16 samples: the Cornell box's error fell by 30%, as clean as twice the samples, and `neon-night`'s by 14%. Both still converge to the same picture. The dreamspace barely changed (−4% at 16 samples, +3% at 64), so its noise must come mostly from elsewhere, likely light bouncing in from the windows. Scenes without glowing boxes are byte-for-byte unchanged.

It isn't free. The dreamspace takes 8% longer per sample, and the Cornell box about 6%. The reason is a nice lesson: a shadow ray aimed at a face pointing away was noticed straight away and dropped *before* it was traced, so the old wasted rays were cheap. Now every shadow ray is aimed somewhere useful, so every one gets traced. The extra time is real work.

What counts is cleanness per second of work, which takes both numbers: error² × time, smaller is better. The Cornell box comes out about 1.9× better and `neon-night` about 1.3×. The dreamspace comes out about even: it pays for shadow rays toward its ceiling panels, but its noise comes mostly from elsewhere.

## A tree of boxes (`scene/bvh.ts`, `intersectScene`)

### 36. Is it worth it? Measure first

A BVH only speeds up one thing: finding which object a ray hits. So before building one, it's worth knowing how much of the time that takes. A quick trick answers it: make every ray do its object tests **twice**, and see how much slower it gets. The extra time is the share of the work that's object tests.

It was 70% in `neon-night` and 90% in the Cornell box and the dreamspace. So object tests were most of the cost, even in the dreamspace with only 34 objects, and a BVH had plenty to win.

### 37. The bounding volume hierarchy

Put a box around groups of objects, boxes around groups of those, and so on, up to one box around everything: a tree. A ray that misses a box skips everything inside it without testing any of it. With n objects, a ray tests roughly log₂ n boxes plus a few objects, instead of all n.

- **The boxes are lined up with the world's axes** ("axis-aligned bounding boxes"), which makes testing one cheap: the same slab test as our boxes, without the turning. Each is padded by 0.1 mm, because a box's faces sit exactly on its bounding box's faces and the two tests round slightly differently.
- **Where to split** follows the **surface area heuristic** (SAH). A ray that hits a box hits a smaller box inside it with a chance proportional to their surface areas. The builder tries every way of splitting the objects, sorted along each axis, and keeps the split with the lowest expected cost. Leaves hold at most 4 objects.
- **It's built on the CPU** when a scene is uploaded, in `scene/bvh.ts`, and tested there. The main test fires 2,000 random rays through every scene and checks the tree finds exactly the same closest object as testing everything.

The tree only skips objects that couldn't be the closest hit, so pictures are byte-identical with and without it.

### 38. The walk, and a lesson about GPU memory

The textbook walk visits the nearer child box first and keeps a list (a **stack**) of farther boxes to come back to. That's what I built first, and it made small scenes **twice as slow**: 3.7 to 8.3 ms for `ball-test-1`.

The reason is memory. Every pixel being worked on kept two lists of 32 entries. A GPU runs thousands of pixels at once, each with its own small, fast memory (registers), and an integrated GPU has very little of it. Big per-pixel arrays get pushed out to slow memory, and fewer pixels can run at once, which slows *everything*.

The fix is a **stackless walk**. Store the tree depth first: a node, then everything in its left child, then everything in its right child. Then the next node is always the right one to visit after a hit, and each inner node keeps one link to the node after its subtree, to follow on a miss. No list is needed. The price is that it can't visit the nearer child first for each ray. That turned out not to matter:

| Scene | Objects | Before | With the BVH | Change |
|---|---|---|---|---|
| `neon-night` | 40 | 14.7 ms | 6.7 ms | −54% |
| `material-test` | 22 | 14.2 ms | 7.9 ms | −45% |
| `aliasing-test` | 14 | 4.9 ms | 2.8 ms | −42% |
| `shadow-heights` | 6 | 3.7 ms | 2.7 ms | −29% |
| `dreamspace` | 34 | 109 ms | 78 ms | −28% |
| `ball-test-1` | 5 | 3.7 ms | 3.4 ms | no clear change |
| `cornell-box` | 8 | 21.3 ms | 21.5 ms | no clear change |

(Path tracer, Intel Iris Xe, plugged in.) The lesson generalizes: on a GPU, how much memory each thread needs can matter as much as how much arithmetic it does.
