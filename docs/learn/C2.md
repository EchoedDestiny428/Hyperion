# C2 in plain words: making samples go further

Read this alongside the code. Each section names the file it explains. C1 made every sample correct and as clean as it could be. C2 makes samples go further: first by sharing them between neighboring pixels (this part, for still images), later by keeping them from frame to frame while the camera moves.

## The denoiser, for still images

### 1. Why the picture stays grainy, and what a denoiser does

Each pixel of a path-traced image is an average of random light paths, so it's off from the true value by a random amount: that's the grain, or **noise**. The error shrinks with the square root of the sample count. Four times the samples only halves it, and that's why the dreamspace's walls were still visibly grainy after 1,024 samples.

But neighboring pixels on the same wall receive almost the same light. Averaging a pixel with 25 neighbors is like borrowing their samples, nearly 25 times as many, for the cost of 25 memory reads instead of 25 times the tracing.

The catch is that a plain average (a **blur**) also smears everything that isn't noise: object edges, the checkerboard, shadow edges, highlights. So a **denoiser** is mostly a way of deciding which neighbors really show the same thing. Photo editors call this an **edge-preserving** or **bilateral** filter ("surface blur" in Photoshop).

Ours follows the spatial half of **SVGF**, "spatiotemporal variance-guided filtering" (Schied et al., NVIDIA, 2017), a standard starting point for real-time path tracing. Its other, temporal half reuses samples while the camera moves; that comes later in C2. The rest of this part goes through what it needs, step by step.

### 2. What each pixel remembers (`render/tracer.wgsl`, `PixelRecord`)

To tell noise from detail, the filter needs to know what each pixel shows. Games keep exactly that in a **G-buffer** ("geometry buffer"): per pixel, the surface's color, which way it faces and how far away it is. In D3D12 or Vulkan it would be a few render targets; here it's part of the same storage buffer as the running total. Each pixel's record grew from one `vec4f` to three (48 bytes), and later four (section 10):

- **`light`**: the running total of light, as in C1, and in its spare 4th value the running total of each sample's brightness *squared*. Section 4 says why.
- **`albedo`**: the running total of the color of the surface the camera ray hit first. It's a total, so it's averaged over the jittered samples like the light: at a checker edge it comes out gray, and the denoised picture keeps its anti-aliased edges.
- **`surface`**: that surface's normal and distance, from sample 0 only. Sample 0 goes through the pixel's center, so it's always the same point; an average of normals across an edge would point a way that neither surface faces.

"The first surface" has two exceptions (`firstSurface` in `tracer.wgsl`), both added after the first measurements (section 8):

- **Mirrors.** In a chrome ball, what needs smoothing is the reflected floor, not the ball, whose own surface would let the filter smear the reflection across it. So the record skips past perfect mirrors to the surface they show, as its **mirror image** (**virtual image**): the image of the floor seems to lie behind the mirror, as far along the camera ray as the reflected path is long, and turned over as a mirror turns things. That turn is a reflection matrix, I − 2nnᵀ (`mirrorMatrix`), multiplied up over every mirror on the way. The path tracer already follows the mirror exactly, so this only watches the path, without a single extra ray.
- **Glowing surfaces** count as nothing to denoise, like the sky. The camera sees their light directly, so it has no noise, and smoothing them only blurs their edges into the wall around them.

Two details keep this from changing the picture:

- **The color comes from `surfaceColor`, not `surfaceAt`.** `surfaceAt` draws random numbers (to pick metal or glass in a blended material), and any extra draw would shift every random number after it, giving a different, equally valid but not identical image. `surfaceColor` draws none, so with the slider at 0 the image is byte for byte the one C1 drew. `npm run noise -- --against <old build>` confirms it: the two differ by 0.00.
- **Memory.** 64 bytes per pixel is about 130 MB at 1920×1080, and about 260 MB at 2560×1600. That's over WebGPU's default 128 MB limit for one buffer, so it relies on `createDevice` asking for the GPU's real limit (C1, section 3). If even that's too small, the image neither refines nor denoises, and the console says so.

### 3. Dividing out the color (`render/denoise.wgsl`, `prepare`)

Light reaching a checkerboard floor is smooth; it's the floor's own colors that change sharply from square to square. So the filter works on **illumination**: the light divided by the surface color. Divided like that, the checkerboard turns into one smooth field of light. The filter smooths that, and at the end each pixel is multiplied by its own color again, so the pattern comes back exactly as sharp as it was. This is **demodulation**, and it's why the denoiser can't blur textures, grout lines or the Cornell box's colored walls into each other.

Old games did the same thing with **lightmaps**: Quake stored lighting as a separate, blurry, low-resolution texture and multiplied it with sharp wall textures at draw time.

A color near zero would turn tiny noise into huge numbers when divided by, so colors below 0.01 count as 0.01 (`ALBEDO_FLOOR`). Multiplying by the same floor at the end undoes it exactly.

### 4. Measuring how noisy each pixel is (`prepare`, `neighborVariance`)

The filter needs to know how much a pixel's value could be off. Statistics has a number for that, the **variance**, the average squared distance from the mean. It's easy to keep track of:

> variance = (average of the squares) − (square of the average)

That's why each record keeps the running total of brightness squared next to the running total of light. Two refinements:

- **The average varies less than one sample.** The screen shows the average of n samples, which varies n times less than a single sample does. So as samples come in, the variance shrinks, and the filter grows stricter and does less. Denoising fades out by itself as the image refines, and pixels that are already clean (a sunlit floor) get less smoothing than noisy ones (a ceiling lit only by bounced light) in the same picture.
- **Bessel's correction.** The mean was worked out from the same samples, which makes the spread around it come out a little small; multiplying by n ÷ (n − 1) corrects that.

With fewer than 4 samples, a pixel's own samples say too little, so `neighborVariance` uses how much its 3×3 neighbors on the same surface differ instead. That counts real detail as noise too, which only matters for the first few samples.

### 5. Who counts as the same (`likeness`, `atrous`)

Each neighbor gets a weight between 0 and 1 from four tests, multiplied together. They're called **edge-stopping functions**, because each one drops to zero across some kind of edge.

- **Facing.** Neighbors on another surface, or around a curve, face a different way. The weight is cos(angle)¹²⁸: 0.88 at 3°, 0.14 at 8°, 0 at 20°. It's computed by squaring seven times rather than with `pow`, because WGSL defines `pow` through `log2`, which has no value at 0.
- **Plane.** From its direction and depth, each pixel's hit point can be rebuilt in 3D. A neighbor on the same flat surface lies in the plane through this pixel's point, so its distance from that plane is about zero. One on an object in front or behind is off the plane. This works even on a floor seen at a grazing angle, where neighbors' distances from the camera differ a lot although they're on the same surface; comparing plain distances would break there. The tolerance grows with the distance and with how far away the neighbor is, measured in pixel widths, so it means the same thing near and far.
- **Color.** Dividing out the color assumes all the light a surface sends back is in proportion to its color, and some isn't: the glint off a surface's glossy top layer is white whatever the color underneath, and haze lies in front of the surface. Divided by a dark color, those come out much brighter than next to a light one. A black checker square would then take in its white neighbors' smaller values and come out too dark. So neighbors whose colors differ count less: by 20%, about a third as much. (SVGF instead splits off the glossy part of the light and filters it separately; that's planned for later in C2.)
- **Brightness.** A neighbor's illumination may differ by up to 4 standard deviations of the noise (the square root of the variance, smoothed over 3×3 pixels because the variance is itself noisy). A bigger difference can't be noise, so it must be detail, like a shadow's edge or a highlight, and the neighbor gets no weight.

Sky and glowing surfaces are never mixed with anything: the camera sees their light directly, so it has no noise to remove.

### 6. À trous: reaching far with few reads (`atrous`, `render/denoise-pass.ts`)

A wide blur would read a lot: 125 × 125 pixels to reach 62 pixels out. Instead, the filter reads a **5×5 grid** with gaps between its points and runs several times, doubling the spacing each time: 1, 2, 4, 8, then 16 pixels. **À trous** is French for "with holes" (Dammertz et al., 2010). Five passes reach 62 pixels from the center with 125 reads per pixel instead of 15,625. Each pass smooths what the one before left: the first removes fine grain, later ones the coarser blotches. (The slider goes to 10 passes, a grid 512 pixels wide, to show that past about 5 more passes change little: most of the grid lands off the screen or on other surfaces. The dreamspace at 16 samples and 640×400 has error 8.6 at 5 passes and 8.9 at both 7 and 10.)

- **The weights within the grid** are the **B3 spline**, 1/16, 1/4, 3/8, 1/4, 1/16 along each axis, a smooth bell shape that doesn't leave a blocky look.
- **The noise is carried along.** Averaging lowers the variance: an average of independent values with weights w has variance Σw²·variance ÷ (Σw)². Each pass writes that next to the illumination, so the next pass's brightness test knows how much noise is left.
- **Two buffers taking turns.** A pixel's new value needs its neighbors' old values, so a pass can't write where it reads. Each pass reads one illumination buffer and writes the other, and the next swaps them: **ping-pong** buffers.

**Compute shaders.** These are the project's first. A fragment shader runs once per pixel of a triangle; a **compute shader** runs once per item of whatever grid you **dispatch**, with no triangle involved. `@workgroup_size(8, 8)` groups the threads into 8×8 tiles, and `dispatchWorkgroups` launches enough tiles to cover the canvas, as `Dispatch` and `[numthreads]` do in D3D12. Threads in tiles hanging over the edge return straight away. All the steps go into one **compute pass**, and WebGPU makes each dispatch see what the one before wrote. In Vulkan or D3D12 you'd insert that **barrier** yourself.

Each pipeline again uses `layout: 'auto'`, which lists only the bindings its own entry point uses, so each one gets bind groups made from its own layout.

### 7. Showing the result (`showDenoised`, `showRaw`, `main.ts`)

The last step multiplies the smoothed illumination by each pixel's average color, then tone maps and sRGB-encodes it, as the tracer does. Tone mapping comes last for the same reason as in C1: averaging has to happen in light, not in screen colors.

- **The filter doesn't run every frame** while the image refines, only when the samples have grown by a tenth; in between, the last filtered light is multiplied by the latest colors (section 9).
- **The slider works on a finished image.** Once the samples are all in, moving the slider redraws from the records already kept, without tracing another sample. Back at 0, `showRaw` shows the plain average.
- **The GPU time covers everything.** One timestamp pair spans the tracer and all the denoiser's passes: the first pass writes the start time and the last the end (`firstAndLast` in `gpu/timer.ts`).
- **Only the path tracer's final image** is denoised. The Whitted renderer has no noise, and smoothing a debug view would hide what it's there to show, so the slider is disabled for them.

### 8. Measuring it, and what the first version got wrong (`scripts/noise.ts`)

`npm run noise -- --denoise 0,1,2,3,4,5` renders every scene at each slider level and compares each picture with a 1,024-sample reference that isn't denoised. So the error counts both the noise a picture still has and anything the filter smeared: a blur always *looks* smoother, but only this says whether it got closer to the truth. `--save <folder>` keeps the pictures, to see what the numbers mean.

**The first version made some scenes worse.** Indoors it was already as good as now, but on the checkerboard scenes the error *rose*, by 64% for `aliasing-test` at 64 samples and level 2. Splitting the picture into blocks and comparing each block's error showed where:

- **the glowing bar in `neon-night`:** its edges were smoothed as if their anti-aliasing were noise. Fixed by never filtering glowing surfaces (section 2).
- **the chrome balls:** the filter smeared their reflections across them. Fixed by recording what the mirror shows (section 2).
- **the far checkerboard:** the floor's glint and the haze aren't in proportion to its color, so dividing by the color made black and white squares disagree (section 5). Fixed by the color test.

After the fixes (and the speedups in section 9, which left these within a few percent), with the default of 2 passes (error, and how many samples the raw picture would need to be as clean; 640×400, checked on 2026-11-10):

| Scene | 4 samples | 16 samples | 64 samples |
|---|---|---|---|
| `dreamspace` | −69% | −72% (13×) | −65% (8×) |
| `cornell-box` | −74% | −73% (14×) | −63% (7×) |
| `material-test` | −57% | −49% (3.8×) | −31% (2.1×) |
| `shadow-heights` | −39% | −30% (2.1×) | −18% (1.5×) |
| `neon-night` | −27% | −14% (1.3×) | −5% (1.1×) |
| `ball-test-1` | −19% | −18% (1.5×) | −13% (1.3×) |
| `aliasing-test` | −4% | −4% (1.1×) | −3% (1.1×) |

What the numbers say:

- **Rooms gain most.** Their light mostly arrives by bouncing, which is the noisiest kind, and the filter has large flat walls to work with.
- **The checkerboard scenes gain least,** because what's left of their error is mostly the far checkerboard's anti-aliasing: noise in the *color* of each pixel, which the filter never touches, since it only smooths light. Sunlit surfaces were also clean to begin with.
- **The table understates the rooms.** The reference has leftover grain of its own, about 4.3 for the dreamspace (estimated from how its error falls as samples grow). Independent errors add like the sides of a right triangle, so of the 6.1 left at 64 samples, the denoised picture's own share is nearer √(6.1² − 4.3²) ≈ 4.3.
- **More passes isn't better.** At 4 samples, 3 to 5 passes help a little more indoors. From 16 samples on, every pass after the second adds more smear than it removes noise, slowly. Hence the default of 2.
- **On the finished image** (1,024 samples), 2 passes change the dreamspace by 4.2, about the size of its leftover grain (4.3), which is what you'd hope: the grain on the ceiling and far wall goes, and the tiles' grout lines and the reflections stay.
- **Slider at 0, the image is unchanged,** byte for byte, in every scene.

### 9. What it costs, and making it cheaper (`render/denoise-schedule.ts`, `packGuide`, `likeness`)

The first working version was far too slow on the laptop's integrated GPU (Iris Xe, on battery, 1280×800): 2 passes added 49 ms to every frame, on top of a 117 ms dreamspace sample, and 5 passes added 90 ms. A single pass cost about 14 ms, several times a whole sample of a simple scene. Three changes, biggest first:

1. **Filter less often** (`needsFilter`). Once a pixel holds a few dozen samples, one more barely changes it, so the filter only runs again when the sample count has grown by a tenth: every sample up to 10, then at 11, 13, 15 … and always at the last one. That's about 60 filters on the way to 1,024 samples instead of 1,024. On the frames in between, `showDenoised` multiplies the last filtered light by the latest colors, which looks the same. A typical refining frame now costs what it did without denoising (`shadow-heights`: 4.1 ms either way). A moving view still filters every frame, since every frame is a new image. Telling images apart takes a **generation** number that goes up whenever the running total starts over.
2. **Read less** (`packGuide`). Each pass reads every pixel's normal, distance and color 25 times. Those used to come from the 48-byte records; `prepare` now packs them once into 16 bytes per pixel, the **guide**: the depth as a full 32-bit float (the plane test needs it exact), the normal at 8 bits per axis (within about 0.3°), and the color as 16-bit floats.
3. **Compute less** (`likeness`). Exponentials and square roots (**transcendental functions**, which GPUs run on a separate, slower unit) and divisions each cost several times a multiplication, and the first version did 9 of them per neighbor. It's down to 2:
   - **The plane test** works from depth along the camera's forward axis instead of distance along the ray. The ray through a pixel, scaled so its forward part is exactly 1, then reaches the hit point at that depth with no square root. The parts of the test that depend only on the center pixel are multiplied out once per pixel (`Center.plane`).
   - **The color test** compares log₂ colors: the ratio between two colors becomes a difference, with no division.
   - **The three tests share one exp,** since e⁻ᵃ·e⁻ᵇ = e⁻⁽ᵃ⁺ᵇ⁾.

Measured with every frame filtered (the "Sun moves" box ticked, so each frame is a new image), `shadow-heights`, 1280×800, on battery: 2 passes now cost 11 to 23 ms, 5 passes 42 to 51 ms, about 10 ms a pass instead of 14. The ranges are real: on battery this laptop's GPU switches between two clock speeds. A test build with the three surface tests taken out, but reading the same memory, was about twice as fast. So the time left is roughly half arithmetic and half reading memory, and making it much faster would take both: keeping neighbors in fast on-chip **workgroup memory** instead of re-reading them, and 16-bit math. That's left for later.

The bigger per-pixel records cost nothing measurable: the dreamspace took 123.3 ms per sample before and 123.0 after, within the benchmark's noise.

A lesson from this: the first guess, that the passes were waiting on memory, was only half right. Measuring a version with one suspect removed is what showed it.

### 10. Bright edges: averaging screen colors where there's no noise (`isNoiseFree`, `screenColor`)

The edges of the dreamspace's ceiling lights looked like staircases when seen at an angle, even after 1,024 samples. That wasn't noise, and only a little of it was the denoiser. It came from the order in C1, section 4: average the light, *then* tone map.

- **Why it crushes the edge.** A panel is about 13 times as bright as the ceiling around it (3.5 against 0.26). A pixel a quarter covered by the panel averages to 1.07, which tone mapping shows at about 80% of white. Even 10% coverage is most of the way to white. So the soft edge anti-aliasing should give is squeezed into one pixel, and an edge at an angle steps. Printing a row of pixels along a panel's lower edge showed values of 146, 208, 227, 234, 240 and up as the coverage slowly grew.
- **Why not just tone map every sample, then average?** That gives the true blend, a quarter of the way from ceiling to panel, which is what games' anti-aliasing does (Brian Karis's "weighted resolve") and what V-Ray calls **sub-pixel mapping**. But for noisy samples it's wrong. Tone mapping is a curve that bends down, and the average of a curve's values is lower than the curve at the average (**Jensen's inequality**). Every noisy pixel would come out too dark, and the image would no longer converge to the truth.
- **What it does instead.** Some samples have no noise: their camera ray went straight to a light or the sky (`isNoiseFree`), so the only thing that varies between them is where in the pixel they land. Those are averaged as screen colors, in a fourth part of each pixel's record (`noiseFree`: the sum of their tone-mapped values, and how many there were). Everything else is averaged as light, as before, and the denoiser only ever sees that part. `screenColor` blends the two by how many samples each has, and all three places that draw the image use it.
- **The result.** The same row along the panel's edge now reads 103, 132, 153, 164, 183, 200 … 248: a smooth ramp. Only pixels along the edges of lights and sky changed: 1,171 in the dreamspace (out of 256,000), 158 in the Cornell box, 240 in `neon-night` (its neon bars, whose stepped magenta fringe became a smooth edge), 228 in `aliasing-test` (the dark ball against the sky), none in the other three. Everywhere else the picture is byte for byte as before. Measured against a reference from an older build, `neon-night`'s error rises, but only because its bars' edges changed. Against its own new reference, the denoiser's gains there are as in section 8: −28%, −15% and −8% at 4, 16 and 64 samples.

**A first try went too far.** It counted any path that reached a light through perfect mirrors as noise-free too. But averaging screen colors caps every sample at white, so a glint smaller than a pixel loses the energy that makes it show. The pink and white glints on `neon-night`'s chrome balls all but vanished. A real camera keeps that energy, and lens glow (**bloom**) spreads it into a visible sparkle. So only lights and sky seen *directly* count, because those are big enough to have edges. A light smaller than a pixel seen directly would still fade; no scene has one.

**What's left:** edges seen in mirrors, through glass or water, and between two noisy surfaces (a sunlit floor next to a shadow) still use the old average, so a very bright one can still step. Bloom, from the plan's list of candidates, would soften those the way a camera does.

**Cost.** The extra 16 bytes per pixel are only written when a sample is noise-free. The record's spare value marks once a pixel has its surface, so the tracer doesn't read it back every sample. Against the build before this change, on the laptop's RTX 4060: light scenes +2% to +7% (about 0.05 ms per sample), `neon-night`, which has the most directly visible sky and light, +0.3 ms.

### 11. What the denoiser doesn't do (yet)

- **Handle a moving camera.** Every move still starts the samples over, and one sample is too few for the filter to work with. Keeping samples from frame to frame is the temporal half of C2.
- **Look through glass and water.** The record stops at their surface, because a path through glass randomly reflects or passes through, so there's no one thing they show. What's seen through them is smoothed as if it were painted on them. Glossy (not perfectly smooth) reflections are treated the same way, guarded only by the color and brightness tests. SVGF filters that light separately; that's planned.
- **Remove fireflies.** A pixel with one rare, very bright sample looks very noisy, so the filter spreads it into a soft blob rather than removing it.
- **Clean up very few samples.** At 1 to 4 samples, what's left is soft blotches: the noise is spread out, not gone.
- **Smooth the color itself.** Grain from anti-aliasing a fine pattern (the far checkerboard) stays, as said above.
